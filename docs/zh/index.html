設計哲學

和重量級 ORM 相反的取捨

重量級 ORM 要求先學會查詢 DSL、session 生命週期與 mapping 儀式 —— 對人是門檻,對 AI 是燒不完的 context 與幻覺的溫床。pymodelet 反過來:尊重 SQL,只接手真正繁瑣的部分。

SQL → object

查詢 → SQL

SELECT 用 ANSI SQL 直接寫 —— 工程師本來就會,模型的訓練語料更是滾瓜爛熟。不發明新的查詢語言:人少學一套 DSL,AI 少燒一份 token、少一個幻覺來源。

object → SQL

寫入 → 框架

INSERT / UPDATE / DELETE 的欄位羅列機械又易錯 —— 人會手滑,AI 會幻覺出不存在的欄位。框架靠 entity 的 TxnMode 自動產生語句、回填主鍵、蓋上稽核欄位,這一整類錯誤直接歸零。

為規模而生

深頁分頁,不付記憶體代價

不論 resultset 是 100 筆還是 50 萬筆,只有你要的那一頁的資料會變成 entity。翻到最後一頁,也絕不把整個 resultset 載進你的應用程式。

實際實體化的 entity 數

LIMIT / OFFSET 下推到資料庫;應用層只映射該頁的列。記憶體與映射成本恆定 —— 第 1 頁或第 5 萬頁都是 O(頁),而非 O(全部)。過去「把全部載進記憶體」的做法已走入歷史。

運作流程

從 SQL 到 entity,再自動寫回

寫 SQL,得到一串 entity。網頁表單透過 Expression Language 把使用者輸入寫進 entity。中間層只要對同一個 entity 呼叫 saveOrUpdate —— Modelet 就把它轉回 SQL。

寫 ANSI SQL

查詢由你作主 —— join、subquery、window function 都行。你和資料庫之間,沒有任何 DSL。

資料列變成物件

model.find(sql, params, Book) 把每一列搬進型別化的 entity。欄位名稱自動對應到欄位。

entity 發生變化

表單或服務直接改動同一個物件;TxnMode 記著它是新的、改過的,還是該刪的。

物件變回 SQL

model.save(entity) 自動產生 INSERT / UPDATE / DELETE、回填資料庫產生的主鍵、蓋上稽核欄位。

entity 用相容 JPA 的註解宣告 —— @Table @Id @Column @Transient @Enumerated @GeneratedValue —— 讀起來和任何 Jakarta Persistence entity 一樣。只借詞彙,引擎始終 SQL-first。

快速開始

一個範例,從頭到尾

經典的一對多:一位 Author 有多本 Book。外鍵就是關聯 —— 沒有 @OneToMany,沒有 lazy loading。

1用相容 JPA 的註解定義 entity

models.pyPython 3.10+
@Table("author")
@dataclass
class Author(Entity):
    name: str | None = None

@Table("book")
@dataclass
class Book(Entity):
    author_id: int | None = None          # FK = the relationship
    title: str | None = Column("bookName")
    price: Decimal | None = None

2用你會的 SQL 查詢

query.pyfind → list
# plain ANSI SQL in, a list of entities out
books = model.find(
    "select * from book where author_id = ? order by id",
    [author_id], Book)

3saveOrUpdate —— 框架幫你寫 SQL

save.pysave
book = Book(author_id=author.id,
            title="pymodelet in Action")
model.save(book)    # new entity → INSERT, id written back

book.price = Decimal("499")
model.save(book)    # loaded entity → UPDATE. same call.

AI 時代

AI 也值得 clean code

「餵給 AI 的框架越乾淨,AI 吐回來的程式就越乾淨。約 600 行、零依賴、沒有 DSL —— 一次就能讀進 context。」規則越少越經典,生成的每一行就越可預測、越好審查。

查詢歸 SQL、寫入歸框架 —— 這條經典的分工,讓「AI 生成、人審查、AI 維護」的循環跑得又快又穩:省下的是 token,換來的是品質與交付速度。

為 AI 精簡

省 token・穩品質・管得動・出得快

整個框架小到 AI 一口氣讀完;查詢用它最熟的標準 SQL,生成即正確的機率遠高於任何自家 DSL;寫入的樣板由框架代勞 —— 幻覺欄位、漏欄位、忘了回填主鍵,這些 AI 最常犯的錯根本沒有發生的空間。context 變小、規則變少,AI 的每一個 token 都花在你的業務邏輯上。
