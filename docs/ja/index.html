設計思想

ORM の潮流とは逆のトレードオフ

2006 年、Hibernate は HQL やセッションのライフサイクル、マッピングの作法を学ばなければ、生産的な一行すら書けませんでした。Modelet は逆です。SQL を尊重し、面倒な部分だけを引き受けます。

SQL → object

クエリ → SQL

SELECT は、エンジニアがすでに知っている ANSI SQL で書きます —— サブクエリも JOIN も。フレームワークは各行をオブジェクトに戻すだけ。新しいクエリ言語はありません。

object → SQL

書き込み → フレームワーク

機械的で間違いやすいのは、INSERT / UPDATE / DELETE のカラム列挙です。Modelet はエンティティの TxnMode 状態から生成し、主キーを書き戻し、監査項目を付与します。

スケール対応

メモリを食わない深いページング

結果セットが 100 件でも 50 万件でも、要求したページの行だけがエンティティになります。最後のページに到達しても、全件をアプリに読み込むことはありません。

500,000

→
10
1 ページあたりの行数
→
10
生成されるエンティティ数

LIMIT / OFFSET はデータベースに委ねられ、アプリ層はページ分の行だけをマッピングします。メモリとマッピングのコストは一定 —— 1 ページ目でも 5 万ページ目でも O(ページ) であり、O(全件) ではありません。「全件をメモリに読み込む」方式はもうありません。

処理の流れ

SQL からエンティティへ、そして自動で戻る

SQL を書けば、エンティティのリストが得られます。Web フォームは式言語 (EL) でユーザー入力をエンティティに束縛します。中間層は同じエンティティに saveOrUpdate を呼ぶだけ —— Modelet がそれを SQL に変換します。

ANSI SQL を書く

クエリはあなたのもの —— JOIN もサブクエリもウィンドウ関数も。あなたとデータベースの間に DSL はありません。

行がオブジェクトになる

model.find(sql, params, Book) が各行を型付きエンティティへ運びます。カラム名は自動でフィールドに対応します。

エンティティが変わる

フォームやサービスが同じオブジェクトを書き換えます。TxnMode が、新規か、変更か、削除かを覚えています。

オブジェクトが SQL に戻る

model.save(entity) が INSERT / UPDATE / DELETE を生成し、採番されたキーを書き戻し、監査項目を刻印します。

エンティティは JPA 互換のアノテーション —— @Table @Id @Column @Transient @Enumerated @GeneratedValue —— で定義され、Jakarta Persistence のエンティティと同じように読めます。借りるのは語彙だけ、エンジンは終始 SQL-first です。

クイックスタート

ひとつの例で、端から端まで

典型的な一対多:Author は複数の Book を持ちます。外部キーがすなわち関連 —— @OneToMany も遅延ロードもありません。

1JPA 互換アノテーションでエンティティを定義

models.pyPython 3.10+
@Table("author")
@dataclass
class Author(Entity):
    name: str | None = None

@Table("book")
@dataclass
class Book(Entity):
    author_id: int | None = None          # FK = the relationship
    title: str | None = Column("bookName")
    price: Decimal | None = None

query.pyfind → list
# plain ANSI SQL in, a list of entities out
books = model.find(
    "select * from book where author_id = ? order by id",
    [author_id], Book)

model.save(book)    # loaded entity → UPDATE. same call.
